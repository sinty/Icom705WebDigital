# Тайные знания

Выяснено экспериментально в этом проекте. В документации ничего этого нет, а часть
прямо противоречит README соседнего проекта `Icom705DigitalDecoder` (он держится
как референс и не правится).

Каждое утверждение здесь получено измерением, а не рассуждением. Методика и
исходные числа приведены, чтобы их можно было перепроверить.

---

## 1. Сигнал с IC-705

### IF-выход НЕ квадратурный

`USB AF/IF Output = IF` отдаёт по USB-кодеку **один вещественный сигнал на ~12 кГц,
продублированный в оба канала со сдвигом ровно в один отсчёт**, а не пару I/Q.

Измерено на `ref/if_master.wav` и `ref/if_dstar.wav`:

```
corr(R[n], L[n-1])  = +1.000000     (оба файла)
лучший целый сдвиг  = -1 отсчёт
```

Один отсчёт при 48 кГц даёт на несущей почти точно 90°:

| файл | несущая | фаза от сдвига в 1 отсчёт |
|---|---|---|
| `if_dstar.wav` | 11969 Гц | 89.8° |
| `if_master.wav` | 12174 Гц | 91.3° |

**Пик спектра — не центр несущей.** Сначала я взял здесь argmax и получил 12711 Гц
для DMR: у 4FSK максимум садится на боковой символьный лепесток, а не на центр.
Правильно брать **центр тяжести горба по усреднённому спектру** — так измеряет
`CarrierEstimator`. Сверка с задокументированными частотами передатчиков из
README соседнего проекта: DMR-рация +12140 против измеренных 12174, ID-52
+11985 против 11969, Yaesu +11962 против 11956 — все в пределах 34 Гц.

Отсюда и подавление зеркала всего **20.9 дБ** — настоящий I/Q-смеситель дал бы
сорок с лишним. «Квадратура» здесь — побочный эффект межканальной задержки АЦП
кодека, а не свойство радио.

### Второй канал избыточен: моно декодируется

Сквозной прогон штатным трактом Pi (`if_demod_offline_iq.py` → `dsd-fme -fs`),
один и тот же эталон, справа он же с принудительным `R := L`:

| метрика | stereo | mono |
|---|---|---|
| Total audio errors | 85 | 101 |
| CRC ERR | 51 | 26 |
| sync | 1299 | 1296 |
| синтезированный голос | 992 684 Б | 979 244 Б |

Разница — 19 %, а не порядок величины. **README соседнего проекта заявляет 3307
против 101 при моно-обработке; это не воспроизводится.** Тот замер, судя по
всему, ловил другой код (`if_demod_offline.py`, «устаревший моно-вариант») или
другой центр, но не моно как таковое.

### Подавление зеркала — негодная метрика качества захвата

Соблазнительно мерить годность сигнала по асимметрии комплексного спектра `L+jR`.
Это ошибка: комплексный перенос на ноль с последующим ФНЧ ±5 кГц выбрасывает
зеркало сам — оно уезжает на −2·f<sub>c</sub> ≈ −25 кГц, далеко за полосу фильтра.
На моно метрика честно даёт 0 дБ, и при этом сигнал прекрасно декодируется.

Мерить надо разброс мгновенной частоты вокруг четырёх уровней 4FSK
(±648 и ±1944 Гц для DMR). Ориентир по эталону: **478 Гц СКО при 19.5 %
отсчётов ближе 200 Гц к уровню**.

Считать «горбы» гистограммы бесполезно — на слабом сигнале счётчик пиков даёт
восемь там, где их четыре.

## 2. Захват в браузере

### Windows по умолчанию открывает USB-кодек в моно

Главная и неочевидная причина, по которой в браузере «пропадает» второй канал.
Проверяется в реестре:

```powershell
$base='HKLM:\SOFTWARE\Microsoft\Windows\CurrentVersion\MMDevices\Audio\Capture'
# формат лежит в свойстве {f19f064d-082c-4e27-bc73-6882a1bb8e4c},0
# ВАЖНО: перед WAVEFORMATEX идёт 8-байтовый префикс,
# nChannels на смещении 10, rate на 12, bits на 22
```

У активных устройств было `ch=1 rate=48000 bits=16`. Лечится в
`control mmsys.cpl,,1` → Запись → Свойства → Дополнительно → Формат по
умолчанию → «2 канала». **После правки Chrome надо перезапустить целиком** — он
кэширует формат устройства при первом обращении.

### `track.getSettings().channelCount` врёт

Возвращает `2`, когда реально приходит один канал. Единственный достоверный
источник — фактическое число каналов в аудиографе (`inputs[0].length` внутри
AudioWorklet). Дополнительно стоит смотреть `track.getCapabilities().channelCount`
и результат строгого запроса `channelCount: {exact: 2}`: строгий запрос
заставляет Chrome отказать вслух вместо тихой подмены на моно.

### Обязательные ограничения захвата

```js
{ channelCount: 2, echoCancellation: false,
  noiseSuppression: false, autoGainControl: false }
```

Проверено: с ними Chrome сообщает «обработка выключена» и не трогает сигнал.

### Ловушка при написании диагностики

Не дублировать канал самим. Конструкция вида `inputs[0][1] || inputs[0][0]`
подставляет копию левого канала, когда правого нет, — и тест потом честно
рапортует «каналы идентичны», измеряя собственный баг вместо браузера.

### Уровень

Пик эталонной записи с Pi — **0.377**. Захват с пиком 0.055 означает, что
`IF Output Level` на радио занижен примерно всемеро. Рабочий диапазон 50–70 %,
при 100 % клиппинг АЦП кодека.

## 3. Сборка dsd-fme в WebAssembly

Порт состоялся; численно эквивалентен нативной сборке. Исходники в
`native/third_party` **не патчатся** — всё изменяемое вынесено в
`native/CMakeLists.txt` и `native/shims/`.

### Шов ввода-вывода уже существует — это PulseAudio

Самое ценное открытие для порта. Весь ввод сходится в **одну** точку —
`getSymbol()` в `src/dsd_symbol.c`, — а та при `audio_in_type == 0` (значение по
умолчанию) читает через `pa_simple_read()`. Поскольку PulseAudio мы всё равно
заглушаем, кольцевой буфер подставляется прямо в заглушку `pa_simple_read`,
а декодированный звук перехватывается в `pa_simple_write`.

Патчить `dsd_symbol.c` и заводить свой `audio_in_type` не нужно.

### Сборка однопоточная

`pthread_create` встречается ровно в одном файле — `rtl_sdr_fm.cpp`, — а сам он
исключается из `SRCS` самим CMake при отсутствии RTL-SDR (`find_package(Threads)`
у них стоит внутри `if(RTLSDR_FOUND)`). Следствие: **SharedArrayBuffer ради
потоков декодеру не нужен**, и требование COOP/COEP на GitHub Pages отпадает.

### Что исключено из сборки

| файл | почему |
|---|---|
| `dsd_ncurses_menu.c`, `_handler.c`, `_printer.c` | терминала в браузере нет |
| `pa_devs.c`, `pulse_devices.c` | перечисление устройств PulseAudio бессмысленно |
| `rtl_sdr_fm.cpp` | RTL-SDR не нужен, и это единственный источник потоков |

Сверх заглушек ncurses и pulse линковщик потребовал ровно два символа:
`ncursesClose` и `pulse_list`.

### `<sys/soundcard.h>` приходится подключать принудительно

`dsd.h` прячет его за `#if defined(__linux__) || defined(__FreeBSD__) || ...`,
которых Emscripten не определяет, — а константы `SNDCTL_DSP_*` и `AFMT_S16_LE`
использует безусловно. Отсюда `-include shims/include/sys/soundcard.h` в
`target_compile_options`.

### CMake 4.x и старые зависимости

libsndfile 1.2.2 требует `-DCMAKE_POLICY_VERSION_MINIMUM=3.5`: совместимость с
`cmake_minimum_required(VERSION < 3.5)` из CMake 4 убрана.

### Лицензии не такие, как кажутся на первый взгляд

«dsd-fme — GPL» звучит правдоподобно и неверно. Основной код dsd-fme и весь
mbelib распространяются под **ISC** (разрешительная). GPL приходит только с
отдельными файлами, и версии у них разные:

| файлы dsd-fme | лицензия |
|---|---|
| `src/fec.c` | GPL-3.0-only |
| `src/rs-12-9.c`, `src/ezpwd/*` | GPL-3.0-or-later |
| `src/dstar_header.c`, `fcs.h`, `descramble.h` | GPL-2.0-only |

libsndfile — LGPL-2.1-or-later.

Следствия: собранный `.wasm` — комбинированное произведение под GPL, и его
распространение несёт обязательства GPL. При этом GPL-2.0-only и GPL-3.0-only
файлы сосуществуют в dsd-fme у самого апстрима — это досталось по наследству,
не создано здесь. Свой код поэтому под ISC: он совместим с любым из этих
вариантов, а не добавляет к путанице ещё одну.

### Версии, на которых всё сходится

| компонент | коммит |
|---|---|
| `lwvmobile/mbelib`, ветка `ambe_tones` | `30dc7907` |
| `lwvmobile/dsd-fme` | `c960f993` (тот же, что собран на Pi) |
| libsndfile | тег `1.2.2` |

mbelib берётся **не апстримный** (`szechyjs`), а форк `lwvmobile` с ветки
`ambe_tones` — так собран рабочий Pi.

### Эквивалентность нативной сборке

Один и тот же демодулированный вход, `dsd-fme -fs`:

| | Pi, нативная aarch64 | WASM в node |
|---|---|---|
| Total audio errors | 85 | 85 |
| CRC ERR | 51 | 51 |
| sync | 1299 | 1299 |
| размер голоса | 992 684 Б | 992 684 Б |

Все решения декодера совпадают до единицы.

### Почему отсчёты всё же расходятся

Совпадает 6.7 % отсчётов, но **корреляция огибающих +0.9949** — речь та же.
Причина: `mbelib.c:32` синтезирует невокализованные участки через
`rand()/RAND_MAX`, а последовательности glibc и musl разные. Обе сборки внутри
себя детерминированы (два прогона на каждой стороне дают одинаковый md5).
Смена коммита dsd-fme (`198f0ea` → `c960f99`) не изменила вывод WASM ни на байт,
так что версия исходников тут ни при чём.

**Практический вывод:** сверять порт по счётчикам ошибок и корреляции огибающих,
а не по хешам файлов.

### Производительность

**x4.3 реального времени** (44.8 с звука за 10.5 с, node, `-O2`, файловый вход).
Сборка с кольцевым буфером и Asyncify — около **x5**. Два экземпляра
(основной + отдельный для YSF, как на Pi) укладываются с запасом.

## 3a. Шов ввода: подводные камни Asyncify

Ввод подан в `pa_simple_read` из кольцевого буфера, ожидание данных сделано
через `emscripten_sleep`, сборка — `-sASYNCIFY`. Работает; выход **побитово
совпадает** с файловым путём (100.00 % отсчётов, RMS ошибки 0.0) при тех же
`sync=1299` и `crc-err=51`. Цена Asyncify: 1.17 → 1.60 МБ (+37 %).

Два грабля, каждый стоил отдельной отладки.

### Состояние, записанное из JS до `callMain`, теряется

Вызов `_dsdw_rb_init()` до `Module.callMain()` отрабатывает успешно и возвращает
живой указатель, но внутри `main` те же статики — нули:

```
[shim] rb_init cap=48001 ptr=0x149f720      <- до callMain
[shim] pa_simple_read #0 bytes=2 ptr=0 cap=0 <- внутри main
```

Рантайм инициализируется в момент запуска `main` и обнуляет статику. **Лечение:**
выделять буфер лениво, при первом обращении из самого шва (`rb_ensure()`), а не
командой из JS заранее. Симптом при этом обманчив: ошибок нет, просто `rb == NULL`,
ветка ожидания не выполняется, и всё выглядит как «Asyncify не работает».

### Пустой буфер должен усыплять декодер, а не отдавать нули

Первая версия по флагу «данных больше нет» заполняла выход тишиной и возвращала
управление. Результат: dsd-fme молотит тишину на полной скорости, `callMain`
никогда не возвращается, страница висит. Единственное правильное поведение —
`emscripten_sleep` в цикле, пока буфер пуст. Тогда простой честно виден в
счётчике (в прогоне на 44.8 с — 252 мс) и процессор не жжётся.

### Проверка шва

`native/test/rb_decode.mjs` подаёт `ref/demod_stereo.wav` через кольцевой буфер
и сверяет выход с `ref/voice_w1.wav`, полученным файловым путём. Обе сборки —
WASM с одним и тем же `rand()` из musl, поэтому при исправном шве совпадение
должно быть побайтовым; любое расхождение означает потерю или дублирование
отсчётов.

## 3b. DSP-тракт: замена GNU Radio на JS

`web/dsp/iq-demod.js` воспроизводит флоуграф `if_demod.py` (перенос на ноль,
ФНЧ, сквелч, ЧМ-детектор) без зависимостей. Проверено на `ref/if_master.wav`:

| сравнение | результат |
|---|---|
| промежуточный сигнал против GNU Radio | корреляция 0.999997, совпадает 97.5 % отсчётов |
| **голос после декодера** | **100.00 % отсчётов, sync=1299, crc-err=51** |

То есть расхождение в 2.5 % отсчётов на демодулированном сигнале (float32 в
GNU Radio против float64 у нас) не меняет ни одного решения декодера. JS-тракт —
побитовая замена.

### Совпадение фильтра с firdes обязательно

`gr_filter.firdes.low_pass` считает число отводов как
`ntaps = int(A·fs / (22·transition))`, где для окна Хэмминга `A = 53`; чётное
значение увеличивается на единицу. При `fs = 48000` и `transition = 2500`
получается **47 отводов**. Дальше — обычный оконный sinc с нормировкой на
единичное усиление по постоянному току. Без этого правила фильтр получится
другой полосы, и сравнивать с эталоном будет не с чем.

### Сквелч в эталонном скрипте отсутствует

`if_demod.py` (живой тракт) содержит `pwr_squelch_cc`, а
`if_demod_offline_iq.py` (которым сделан `ref/demod_stereo.wav`) — **нет**.
При сверке с эталоном сквелч надо выключать, иначе расхождение необъяснимо.

### Блочная обработка эквивалентна сплошной

AudioWorklet отдаёт блоки по 2048 отсчётов, и состояние (линия задержки ФНЧ,
фаза гетеродина, предыдущий отсчёт детектора) обязано переноситься через границу.
`test/chain_check.mjs` гоняет файл блоками и сверяет с эталоном: 100.00 %
совпадения. Любое расхождение здесь означает потерю состояния.

### Моно через полную цепочку

`sync=1296`, `crc-err=26`, голос 489 600 отсчётов — **ровно те же числа**, что
дал моно-прогон нативной сборки на Pi. Ещё одно подтверждение, что второй канал
избыточен.

## 3c. Браузерная обвязка: грабли

### `.mjs` под `python -m http.server` не запускается

Штатный `http.server` отдаёт `.mjs` как **`text/plain`**, а браузер отказывается
исполнять модуль с неверным типом содержимого. Импорт WASM-модуля внутри воркера
падает, воркер не стартует — и никаких следов: лог пуст, страница выглядит живой.

Отсюда `tools/serve.py`, где типы поправлены (`.mjs`, `.js` → `text/javascript`).
GitHub Pages отдаёт `.mjs` правильно, так что проблема только у локального
сервера. Проверять так:

```bash
curl -sI http://127.0.0.1:8000/native/build/dsd-fme-rb.mjs | grep -i content-type
```

**Одной правки сервера не хватает.** Chrome запоминает ответы с прежним типом,
и `Cache-Control: no-store` на уже сохранённые записи не действует: после
починки сервера воркер продолжал не загружаться. Лечится жёсткой перезагрузкой
(Ctrl+Shift+R) — а чтобы это не повторялось, URL воркера получает версию
(`?v=<время>`), и она пробрасывается в его зависимости. Поэтому импорты в
`web/worker/decoder.js` динамические: к статическому `import` версию не
приписать, и его отказ вообще нечем поймать.

### Сервер разработки обязан быть многопоточным

Однопоточный `socketserver.TCPServer` виснет: порт слушается, а ответов нет —
одна брошенная посередине или залипшая connection блокирует обработку, а
страница тянет модули и wasm параллельно. Штатный `python -m http.server`
не случайно использует `ThreadingHTTPServer`; в `tools/serve.py` теперь тоже он.
Симптом легко спутать с ошибкой в коде страницы.

### Ошибки воркера обязаны быть видны

Первый прогон на железе провалился именно из-за этого: без `worker.onerror`
несостоявшаяся загрузка модуля не оставляет вообще никакого следа. Обязательный
минимум — `worker.onerror`, `worker.onmessageerror` и глобальные слушатели
`error` / `unhandledrejection`, выводящие в тот же лог, что и декодер.

### Самопроверка без радио

Кнопка «Самопроверка без радио» подаёт `ref/demod_stereo.wav` уже
демодулированным, в темпе реального времени, минуя захват и DSP. Это разделяет
два класса неисправностей: если самопроверка идёт, а с радио тишина — виноват
захват, а не декодер.

## 3d. Почему вокодер от прошивки MD380 остался за бортом

**md380-emu — это не эмулятор.** Название вводит в заблуждение, и на этом легко
потерять время. В `md380tools/emulator/` лежат 414 строк обвязки, которые:

- вшивают образ прошивки в ELF-секцию по адресу `0x0800C000`, а дамп ОЗУ — по
  `0x20000000`;
- берут адреса функций прошивки из `applet/src/symbols_d02.032`;
- **вызывают ARM-код Thumb-2 напрямую как нативные функции**, собираясь
  `arm-linux-gnueabi-gcc -static`.

Из README проекта: работает только на 32-битном ARM Linux либо под `qemu-user`.
Процессорного эмулятора в md380tools нет вообще — эмуляцию делает qemu.

Значит, для браузера понадобился бы интерпретатор Cortex-M4 (Thumb-2 плюс
DSP-инструкции), собранный в WASM. Готового в комплекте нет, и это была бы
самая крупная работа в проекте — больше, чем порт dsd-fme.

### Что при этом устроено удобно, если когда-нибудь понадобится

Поверхность крошечная — один вход:

```c
ambe_decode_wav(outbuf, 80, bits, 0, 0, timeslot, state)
```

Буферы по фиксированным адресам ОЗУ (вход `0x20011c8e`, выходы `0x20011aa8`
и `0x20011b48`, состояние `0x20011224`), начальное состояние берётся из готового
дампа — ни загрузки, ни периферии моделировать не нужно.

Блобы: **дампы ОЗУ `cores/*.img` (128 КБ) и таблицы символов лежат прямо в
репозитории md380tools**, от пользователя нужна только прошивка. И не любая:
`md380-emu` пришпилен к версии **D002.032**. Манифест `firmware/firmware_files.txt`
даёт точный URL и SHA-256 каждой версии (для D002.032 —
`e1a1a11a84d9afd2d2ceed61be8395e32a8034785abd0be0236478f7d8609f43`), качается
с md380.org, не с сайта TYT.

Проверять было бы на чём: собрать нативный md380-emu на Pi (aarch64 умеет armhf,
иначе `qemu-user`), продекодировать приложенный `sample.amb` и получить
golden-файл.

**Решение: остаёмся на mbelib.** Он работает, голос разборчив, блобов не нужно,
привязки к версии прошивки нет. Если качества когда-нибудь не хватит — путь
описан выше, начинать с golden-файла на Pi.

## 3e. Панорама: что делает её похожей на родной экран

Строение и палитра сняты с фотографии экрана IC-705. Три детали, без которых
сходства не получается, и каждая была сделана неправильно с первой попытки:

- **Это два блока, а не один.** Сверху заполненная спектральная кривая по сетке
  (`Grid 20k/10dB` — десять делений по горизонтали, по 10 дБ по вертикали, доля
  высоты около 45 %), под ней полоса частотной шкалы в килогерцах от центра
  (`-80…+80`), ниже водопад. Один водопад без спектра не похож вообще.
- **Пол водопада синий, а не чёрный.** Шум на родном экране выглядит синим
  полем, а не темнотой. Дальше синий → голубой → зелёный → жёлтый → красный →
  белый.
- **Водопад идёт сверху вниз.** Новая строка появляется вплотную к спектру,
  история уезжает вниз. Привычные SDR-водопады дописывают новое снизу, и по
  инерции легко сделать наоборот.

Границы отображения (пол и потолок) обязаны быть настраиваемыми: сырые значения
в кадрах идут `0..0xA0`, но куда попадает шумовая полка, зависит от усиления и
REF на радио.

`tools/scope-preview.html` гоняет настоящий код отрисовки на синтетическом
сигнале — подгонять внешний вид можно, не занимая радио.

## 4. Эталонные записи

В `ref/` лежат снятые с Pi образцы. Все стерео 48 кГц s16 (`pw-record` без флагов
формата; живой тракт на Pi использует f32 — на анализ не влияет).

| файл | что |
|---|---|
| `if_master.wav` | DMR, 44.8 с — основной эталон |
| `if_dstar.wav` | D-STAR, 39.6 с |
| `if_ysf.wav` | YSF, 39.8 с |
| `demod_stereo.wav` | `if_master.wav`, прогнанный через демодулятор Pi — вход для регрессии декодера |

гоняться за эфиром.
